# v0.2 design note: pluggable source providers

Status: design only. This document does not change v0.1 behavior.

## Goal

Separate field acquisition from the orchestration pipeline so an operator can choose an authorized API, a public browser reader, or a controlled fallback order without changing canonical resolution rules. Providers return evidence and access state; they do not write canonical values or decide approval.

## Interface

```text
SourceProvider
  name: stable provider identifier
  supports(requested_fields, country) -> capability result
  health(run_context) -> healthy | degraded | blocked
  estimate(query, requested_fields) -> request count and estimated cost
  discover(query, limit, cursor?) -> businesses, evidence, next cursor
  read(business_ref, requested_fields) -> observations, evidence, access result
```

Every call receives a run-scoped context containing timeout, retry budget, rate limit, country, and an opaque credential reference. Results carry provider name, retrieval time, source URL or provider record ID, raw snapshot digest, field, status, and machine-readable restriction/error category. Providers never receive outreach or messaging capabilities.

## Implementations

### Google Places API provider

Use an official Places API client configured by the operator. Discovery maps text/nearby search results into business candidates. Place Details supplies supported fields. API denials, quota exhaustion, and billing/configuration failures become provider health events; they are not `not_public`.

### Browser scraper provider

Use the existing isolated reader against publicly accessible pages. It stores immutable snapshots and emits only literal observations. Login prompts, consent barriers that cannot be completed safely, limited views, CAPTCHAs, and rate limits produce `access_restricted`. Consecutive restrictions degrade and eventually block this provider for the run.

## Field mapping

| Canonical field | Places API candidate | Browser candidate | Notes |
|---|---|---|---|
| `business_name` | display name | listing heading | Identity must still be corroborated. |
| `google_rating` | rating | visible listing rating | Numeric validation remains canonical. |
| `google_review_count` | user rating count | visible review count | Never borrow counts from related listings. |
| `public_contact` | national/international phone, website | visible phone or official site | Preserve source and normalized value separately. |
| `instagram` | normally absent | official-site link or verified public profile | Requires business-identity corroboration. |
| `whatsapp` | normally absent | explicit WhatsApp link or label | A phone number alone is insufficient. |
| `owner` | normally absent | explicit public owner/founder statement | Never infer from staff names. |
| `dm_proxy` | unavailable | public proxy components only | No messages are sent. |

Unsupported fields are not silently reported as absent. The provider returns unsupported capability metadata, allowing another provider to try them.

## Cost model

Costs must be calculated from the provider's current configured price table rather than embedded as permanent constants.

```text
estimated_run_cost =
  discovery_requests × discovery_unit_price
  + detail_requests × detail_unit_price
  + optional_field_requests × field_unit_price
```

For reporting, expose estimated and actual requests, billed field groups/SKUs where available, cache hits, and estimated cost per accepted business. A useful comparison is total provider cost divided by unique canonical businesses, not by raw candidates. The browser provider has no per-request API fee but still has compute, proxy, browser, and operator costs; those should be configurable estimates rather than represented as zero.

## Keys and configuration

Configuration should select providers and refer to credentials by environment-variable name, never embed secrets:

```yaml
sources:
  google_maps:
    providers:
      - type: google_places
        api_key_env: GOOGLE_PLACES_API_KEY
        price_table: config/provider-prices.json
        daily_budget: 10.00
      - type: browser
        profile: public-isolated
        consecutive_restriction_limit: 3
```

Startup validates that required keys exist without logging values. Run metadata records provider type, configuration digest, API/version identifier, request counts, and effective budgets. Secret values and full authorization headers must never enter snapshots, metrics, failure records, or reports.

## Fallback order

1. Prefer an explicitly configured authorized API for fields it supports.
2. Use cached API evidence when it remains within the configured freshness window.
3. Use the public browser provider only when enabled and permitted for the intended use.
4. If one provider is restricted, over budget, or blocked, try the next configured provider after recording the health transition.
5. If every capable provider is unavailable, return `access_restricted` or `error` according to the observed cause—never `not_found` or `not_public` merely because access failed.

Fallback must remain field-specific: an API may resolve rating and review count while the browser provider handles an explicitly linked Instagram account. Resolution and acceptance remain provider-independent and continue to require evidence provenance.
